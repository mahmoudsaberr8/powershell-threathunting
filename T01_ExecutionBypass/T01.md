# Technique 01 — Execution Policy Bypass
## Lab Documentation | Windows 10 Home
**MITRE:** T1059.001 | **Severity:** High | **Status:** Partially Mitigated (Home Edition Limitation)

---

## What This Attack Does

The `-ExecutionPolicy Bypass` flag lets an attacker run any PowerShell script
regardless of the machine's execution policy setting. No admin rights needed.
It works because the default Execution Policy lives in the user registry hive
(`HKCU`) which command-line flags can override freely.

---

## Before — Attack Works (Baseline)

### Step 1 — Check current Execution Policy

Command run:
```powershell
Get-ExecutionPolicy
```

![Baseline execution policy check](screenshots/T01/01_baseline_get_executionpolicy.png)

Result: `Undefined` across all scopes — zero enforcement in place.

### Step 2 — Run the bypass attack

Command run:
```powershell
powershell.exe -ExecutionPolicy Bypass -Command "Write-Host 'Bypass worked'"
```

![Bypass attack succeeds before hardening](screenshots/T01/02_bypass_attack_succeeds.png)

Result: `Bypass worked` — the attack runs freely with no restriction.

---

## Fix Applied — Registry Approach (Home Edition Method)

On Windows 10 Home, `gpedit.msc` does not exist. Every GPO setting writes
to the registry under the hood — so we write directly to the same registry
paths that GPO would use.

### Step 1 — Create the PowerShell policy registry path

Command run (as Administrator):
```powershell
New-Item -Path "HKLM:\SOFTWARE\Policies\Microsoft\Windows\PowerShell" -Force
```

![New-Item creates the PowerShell policy registry key](screenshots/T01/03_newitem_registry_key.png)

**What this does:** Creates the folder in the registry where Windows reads
machine-level PowerShell policy. This is the exact path GPO would write to.

---

### Step 2 — Write the ExecutionPolicy value

Command run:
```powershell
Set-ItemProperty -Path "HKLM:\SOFTWARE\Policies\Microsoft\Windows\PowerShell" `
  -Name "ExecutionPolicy" `
  -Value "AllSigned" `
  -Type String
```

**Why AllSigned:** Only scripts signed by a trusted publisher run.
An attacker's unsigned malware.ps1 is refused. Strictest available option.

## Issues Encountered (Home Edition Reality)

### Issue 1 — Wrong registry path created

**What happened:** The key was accidentally created at:
```
HKLM:\SOFTWARE\Microsoft\Windows\PowerShell       ← WRONG
```
Instead of the correct path:
```
HKLM:\SOFTWARE\Policies\Microsoft\Windows\PowerShell  ← CORRECT
```
PowerShell only reads MachinePolicy from the `Policies` hive. The wrong
location has zero effect. Fixed by navigating regedit manually to the
correct path and creating the key there.

![Regedit showing correct path with ExecutionPolicy = AllSigned](screenshots/T01/04_regedit_correct_path.png)

### Issue 2 — MachinePolicy scope stays Undefined on Windows 10 Home

**What happened:** Even with the registry key in the correct location,
`Get-ExecutionPolicy -List` continued showing `MachinePolicy = Undefined`.

**Root cause:** Windows 10 Home does not feed the `HKLM\SOFTWARE\Policies`
hive into PowerShell's `MachinePolicy` scope. This requires the Group Policy
Client to apply machine-level policy — which Home edition supports for
`gpupdate /force` but not for PowerShell's execution policy scope.

Evidence — `gpupdate /force` ran successfully:
```
Computer Policy update has completed successfully.
User Policy update has completed successfully.
```

But `Get-ExecutionPolicy -List` still showed:
```
MachinePolicy    Undefined
```

![gpupdate force completes but MachinePolicy still Undefined](screenshots/T01/05_gpupdate_machinepolicy_undefined.png)

**This is a known Windows 10 Home limitation — not a configuration error.**

---

### Workaround Applied — LocalMachine Scope

Command run:
```powershell
Set-ExecutionPolicy AllSigned -Scope LocalMachine -Force
```

```powershell
Get-ExecutionPolicy -List
```

Result:
```
        Scope ExecutionPolicy
        ----- ---------------
MachinePolicy    Undefined
   UserPolicy    Undefined
      Process    Undefined
  CurrentUser    Undefined
   LocalMachine    AllSigned    ← Workaround applied here
```

![LocalMachine scope set to AllSigned](screenshots/T01/06_localmachine_allsigned.png)

## Key Learning — Why the Bypass Still Worked

```
MachinePolicy scope  → Written by true Group Policy
                     → CANNOT be overridden by -ExecutionPolicy flag
                     → NOT available on Windows 10 Home

LocalMachine scope   → Written by Set-ExecutionPolicy
                     → CAN be overridden by -ExecutionPolicy flag
                     → Available on all editions including Home
```

`LocalMachine` scope is not the same as `MachinePolicy` scope.
The `-ExecutionPolicy Bypass` flag can override `LocalMachine` but
cannot override `MachinePolicy`. On Home edition, the real protection
against this attack comes from Technique 03 — `__PSLockdownPolicy = 4`
which forces Constrained Language Mode at a level below execution policy.

---

## What Actually Stops This Attack on Windows 10 Home

```
Technique 01 alone (LocalMachine scope):     Partial — flag can override it
Technique 03 (__PSLockdownPolicy = 4 + CLM): Full — blocks at kernel level
Combined:                                    Full coverage
```

CLM (Constrained Language Mode) removes `Invoke-Expression`, `Net.WebClient`,
and .NET type access from PowerShell entirely — regardless of execution policy
settings or bypass flags. Applied in Technique 03.
